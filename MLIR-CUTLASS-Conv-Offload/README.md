# MLIR-CUTLASS-Conv-Offload

This project takes ResNet50 — all 53 of its convolution layers — and compiles it down to one GPU program. Every convolution runs on a hand-tuned CUTLASS kernel. Every other operation (batch-norm, ReLU, pooling, matmul) runs as a CUDA kernel generated by MLIR. The pipeline starts with `resnet50.py`, which exports the model to MLIR using torch-mlir, and ends with a fully lowered `.mlir` file that can run on a GPU.

## Directory structure

```
MLIR-CUTLASS-Conv-Offload/
├── Analysis-Passes/           MLIR passes that trace how linalg ops depend on each other
├── Transformation-Passes/     MLIR passes that lower conv2d to CUTLASS
├── CUTLASS-wrapper/           CUDA/CUTLASS kernels and benchmarks
├── MLIR-logs/                 saved IR from different stages
├── resnet50.py                exports ResNet50 to MLIR using torch-mlir
└── Report.pdf
```

## Analysis passes

Before any code is rewritten, the analysis passes work out how the linalg ops relate to each other. One pass goes through every linalg op, notes what each op produces and what inputs it uses, and then, for each op, looks up which other op produced each of its inputs. The other pass simply lists the ops in order.

With dozens of convolutions mixed in with batch-norm, ReLU, and pooling across ResNet50's blocks, this is what lets you know exactly which op feeds into each convolution, and where it sits among its neighbors, before deciding to replace it.

## Transformation passes

This is a rewrite pass that finds every `linalg.conv_2d_nchw_fchw` op and replaces it with a call to an external function, `cutlass_conv2d_kernel`. It passes in the output, input, and filter buffers, plus the convolution's shape, stride, padding, and dilation. Nothing else in the model is touched. There are two versions of this pass: one works on tensor or memref IR and replaces the conv op's output value; the other works only on memref IR and just deletes the conv op, since the output buffer is already written in place by the CUTLASS call.

This holds across the whole model, not just a few ops. Comparing the IR before and after the pass (saved in `MLIR-logs/`) shows it acting on every layer:

- Before: **53** `linalg.conv_2d_nchw_fchw` ops — one per convolution in ResNet50 — and zero CUTLASS calls.
- After: **0** `linalg.conv_2d_nchw_fchw` ops left, and **53** calls to `cutlass_conv2d_kernel` in their place.

Everything besides the convolutions is unchanged between the two files. The pass touches every conv op in the model, and nothing else.

## CUTLASS side

`cutlass_conv2d_kernel` isn't part of CUTLASS itself — it's a bridge function (`CUTLASS-wrapper/cutlassConv2dMlirBridge.cu`) that unpacks the memref descriptors MLIR passes in (pulling the raw float pointers out of them) and uses them to run a CUTLASS convolution. MLIR's tensors are laid out NCHW, but CUTLASS's kernel here is built for NHWC, so the bridge first runs its own small CUDA kernels to transpose the input and filter into NHWC before handing them to CUTLASS. Internally, CUTLASS treats the convolution as a matrix multiply (an "implicit GEMM"), using its `Conv2dFprop` kernel template built for NVIDIA SM80 GPUs. The `CUTLASS-wrapper/` folder also has a plain CUTLASS convolution benchmark and a naive CUDA convolution benchmark, kept separate from the MLIR path, to compare against.

## What the IR looks like after transformation and full lowering

`MLIR-logs/` has full snapshots of the model's IR at three points: bufferized linalg before the transformation, bufferized linalg right after the CUTLASS rewrite, and the final version after standard MLIR lowering to LLVM/NVVM and the GPU dialect.

That final file is the end result of the whole pipeline, and two things hold true across it:

1. **All 53 CUTLASS calls make it through lowering.** They show up as `llvm.call @cutlass_conv2d_kernel(...)`, going through an `_mlir_ciface_*` wrapper that turns the memref data into the plain pointers and sizes CUTLASS expects.
2. **Everything else becomes GPU kernels.** The non-convolution ops are fused and turned into hundreds of small `gpu.func`-style kernels. Each one is launched from the host with a `gpu.launch_func` call (with grid size, block size, and arguments spelled out) and is built internally from NVVM instructions for the GPU.

The scale shows directly in the file: **422** `gpu.launch_func` calls alongside the **53** CUTLASS calls, all inside one module. The end result is one compiled program, built from a single high-level model description, where every part of ResNet50 — convolutions included — runs on the GPU.
